# 员工门户 · 密码找回演示

一个可实际启动的密码找回（忘记密码）演示系统：员工通过邮箱收到一次性随机链接，
在 10 分钟内设置新密码，重置成功后旧密码与该账号的全部旧会话同时失效。

技术栈：**FastAPI + SQLite（WAL 模式）+ argon2-cffi**，
附带一个与业务库**完全隔离的独立演示邮箱库**，浏览器即可完成完整找回流程。

## 一、快速启动

### 方式 A：Docker Compose（推荐，两个 Web 进程）

```bash
docker compose up --build
```

启动后浏览器打开：

- 进程 1：<http://localhost:8001/>
- 进程 2：<http://localhost:8002/>

两个进程共享同一个 SQLite 数据卷（`portal-data`），用于演示跨进程并发。
停止并清空数据：`docker compose down -v`。

### 方式 B：本地直接运行（无需 Docker）

```bash
python3 -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt
./run_local.sh
```

打开 <http://127.0.0.1:8001/>。数据落在 `./data/`，重启进程不丢失。

### 预置账号

| 用户名 | 邮箱 | 初始密码 |
|---|---|---|
| `alice` | `alice@example.test` | `Wonderland-1` |
| `bob` | `bob@example.test` | `Secret-2` |

## 二、浏览器演示流程

1. 用 `alice / Wonderland-1` 登录，进入 **我的身份** 查看当前会话与密码版本。
2. 打开 **找回密码**，输入 `alice`（用户名或邮箱均可），提交申请。
3. 打开 **演示邮箱** → `alice@example.test` → 最新邮件，点击邮件中的链接。
4. 在打开的页面设置新密码并提交，看到“密码重置成功”。
5. 回到 **我的身份**：原会话已被撤销，被要求重新登录；旧密码无法登录，新密码可以登录。
6. 再次打开同一封邮件里的链接：提示“已被使用过”，不能重复重置。

## 三、核心问题与修复：签发与投递的配对发布

### 修复前的缺陷

旧实现先在业务库提交令牌（旧链接立即作废、新链接生效），**之后**才写邮件，
且邮件写入异常被静默吞掉、页面一律显示“已发送”。当邮箱库写锁超时或写入失败时，
系统会同时出现三种撕裂状态：

- 页面谎称邮件已发送；
- 旧链接已作废、新链接却没有对应邮件（有效链接无邮件）；
- 若进程在两步之间退出，重启后也没有任何机制收敛残留状态。

### 修复方案：两库状态机 + 配对发布 + 失败补偿 + 崩溃恢复

业务库与邮箱库是两个独立 SQLite 文件，无法用单事务原子提交，
因此用状态机把跨库操作收敛到与原子提交等价的效果：

```
业务库 reset_tokens.status:  pending → active → consumed / superseded
                                      └→ aborted（投递失败 / 崩溃补偿）
邮箱库 mails.status:         pending → sent（收件人可见）
                                      └→ aborted（失败撤回，不可见）
```

一次申请（`app/service.py::request_password_reset`）的步骤：

1. **签发 pending 令牌**：业务库短事务写入 `pending` 令牌（此状态下任何链接核验
   一律无效），不动任何已发布的旧链接；事务立即提交并释放业务库写锁。
2. **写入 pending 邮件**：在独立的邮箱库短事务写入 `pending` 邮件。
   等待邮箱库写锁就发生在这一步，与业务库写锁完全无关——**等待期间不持有业务库
   写锁**，其他账号仍可登录、查询身份、申请重置。
3. **配对发布**：先把邮件置为 `sent`（用户可读），再在业务库单事务里把本令牌置为
   `active` 并作废该账号旧的 `active` 链接。于是“**新邮件可读、新链接生效、旧链接
   作废**”三者一起对外生效。
4. **失败补偿**：任一步失败，只按本申请的 `request_id` 把自己的 pending 记录
   回滚为 `aborted`（必要时撤回已发布的邮件），绝不触碰其他申请；页面明确显示
   “投递失败，本次申请未生效”，**不会谎报已发送**，申请前状态完整保留。
5. **崩溃恢复**：进程在发布中途退出后，残留的 pending 记录由启动恢复与每 5 秒
   一次的定时恢复，按两库 `request_id` 配对关系收敛：
   - 邮件不在/已撤回 → 令牌作废；
   - 令牌不在/已作废 → 邮件撤回；
   - 邮件已 `sent`、令牌仍 `pending` → 补发布令牌并作废旧链接；
   - 两边都 `pending` → 双双作废。
   恢复有宽限期（默认 20 秒，避开正常处理中的年轻 pending），且幂等。

### 关键不变量（测试中逐场景断言）

- 业务库不存在长期 `pending` 令牌，邮箱库不存在长期 `pending` 邮件；
- 每个有效链接（active/consumed/superseded）必有一封 `sent` 邮件，反之亦然；
- 永远不会出现“有效链接无邮件”或“可见邮件对应未签发链接”；
- 并发申请时，一笔失败的收尾只撤销自己，撤销不了另一笔成功申请。

## 四、其余安全语义与实现位置

| 需求 | 实现 |
|---|---|
| 随机链接 10 分钟有效 | `app/config.py` 的 `RESET_TTL_SECONDS=600`；写入 `expires_at`，每次核验都比较当前时间 |
| 业务库仅存令牌摘要 | `secrets.token_urlsafe(32)` 生成 256bit 令牌；库里只存 SHA-256 摘要，原始令牌只出现在邮件里 |
| 签发新链接即作废旧链接 | 令牌发布事务内 `UPDATE ... SET status='superseded' WHERE user_id=? AND status='active' AND request_id<>?` |
| 哈希计算不持写锁 | Argon2 哈希/校验全部在写事务**之外**执行，慢哈希期间仍可申请链接、登录、查身份 |
| 重置三件事一起生效 | `commit_password_reset` 单 `BEGIN IMMEDIATE` 事务：条件消费链接 → 换密码并 `password_version+1` → 删除该账号全部会话 |
| 同链接并发只成功一次 | 条件 `UPDATE ... WHERE status='active' AND expires_at>now` + 检查 `rowcount`，跨进程只有一个赢家 |
| 旧链接在途重置失败 | 在途重置最终提交重新核验状态；旧链接已 `superseded`，条件 UPDATE 命中 0 行，整体回滚 |
| 旧密码核验跨越重置不发会话 | 登录在慢哈希后、写事务内复查 `password_version`，期间被重置则放弃会话 |
| 重置/投递失败不改状态 | 失败路径回滚或补偿；只读核验函数绝不改状态 |
| 重启保留数据与自愈 | SQLite 文件存于数据卷；启动 + 定时恢复收敛 pending 残留 |
| 旧版库平滑升级 | `init_storage` 自动把旧的 `consumed_at/superseded_at` 结构迁移到状态机 |

### 为什么用 WAL + IMMEDIATE

- `PRAGMA journal_mode=WAL`：读不阻塞写、写不阻塞读，多进程可同时读；
- 每个写事务 `BEGIN IMMEDIATE` 立即取得保留锁，配合各自独立的 `busy_timeout`
  （业务库 5s、邮箱库 5s，可用环境变量调整）排队等待；
- 一次性消费全部靠**条件 UPDATE + rowcount** 在单事务内判定，
  两个独立 OS 进程并发时同一条链接也只能成功一次。

## 五、可控故障演示（页面操作，无需改代码）

打开 **哈希延迟与故障演示**（`/settings`）页，所有开关持久化在业务库、触发一次后
自动复位：

| 演示项 | 操作 | 预期现象 |
|---|---|---|
| 邮箱锁等待 | 邮箱锁占用设 2000ms 后申请 | 申请在邮箱库排队约 2 秒后成功；等待期间用另一窗口登录/查身份立即响应 |
| 投递失败（锁超时） | 邮箱锁占用设 8000ms（> 邮箱 busy_timeout 5s） | 约 5 秒后页面显示“投递失败，本次申请未生效”，邮箱无邮件，无 pending 残留，旧密码仍可登录 |
| 投递失败（分阶段注入） | 选择故障阶段（邮件落库/邮件发布/令牌发布）后申请 | 三阶段任一失败都整笔补偿，页面不报已发送，旧链接保持有效 |
| 发布中进程退出 | 选择退出阶段后申请 | 该 Web 进程 `os._exit(1)` 硬退出；Compose 自动重启，启动恢复收敛 pending，无“有效链接无邮件 / 可见邮件无有效链接” |

页面下半部分实时显示两库各状态的记录数量与最近事件日志，便于观察每一步。

## 七、目录结构

```
app/
  config.py       # 配置（环境变量可调：锁超时、恢复宽限期等）
  db.py           # SQLite 连接、WAL、状态机建表、旧库迁移、写事务助手
  security.py     # Argon2 哈希/校验、随机令牌、SHA-256 摘要、会话标识
  service.py      # 业务服务层（配对发布 saga、补偿、崩溃恢复、令牌生命周期、邮箱）
  main.py         # FastAPI 路由与页面（lifespan 启动/定时恢复）
  templates/      # Jinja2 页面
tests/            # pytest 测试
Dockerfile
docker-compose.yml  # 两个 Web 进程 + 共享数据卷
run_local.sh      # 无 Docker 本地双进程启动
```
